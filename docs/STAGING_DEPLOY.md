# Серверное развёртывание MISTERCHIP

Этот документ описывает сценарии из репозитория. Он не является отчётом
о текущем состоянии рабочего сервера. Для знакомства с приложением используйте
[локальный запуск](LOCAL_DEVELOPMENT.md).

## Состав серверного окружения

[compose.staging.yaml](../compose.staging.yaml) запускает PostgreSQL, Redis
и приложение под Gunicorn. Статика собирается при запуске контейнера
и обслуживается WhiteNoise. Исходный каталог хоста в контейнер приложения
не монтируется.

HTTP-порт приложения привязан к `127.0.0.1:8000`. Порты PostgreSQL и Redis
наружу не публикуются. Секреты читаются из серверного `.env`;
данные базы, Redis и тестовой почты хранятся в volumes.

## Два режима доступа

| Режим | Сценарий и ожидаемые настройки |
| --- | --- |
| Закрытый стенд через SSH | [ops/deploy-host.sh](../ops/deploy-host.sh), `DJANGO_DEBUG=0`, `DJANGO_STAGING_SSH_TUNNEL=1`, разрешены только локальные хосты. |
| Публичный HTTPS через прокси | [ops/deploy-public-host.sh](../ops/deploy-public-host.sh), `DJANGO_DEBUG=0`, `DJANGO_STAGING_SSH_TUNNEL=0`, доверенный HTTPS-прокси, явно заданные домен, allowed hosts и CSRF origins. TLS завершает отдельно настроенный Caddy. |

В обоих сценариях сейчас проверяется
`django.core.mail.backends.filebased.EmailBackend`: письма сохраняются
в закрытый volume `mail_data`. Наличие HTTPS-сценария само по себе не означает,
что настроена доставка реальной почты. Для перехода на SMTP требуется
согласованно изменить конфигурацию и проверки серверного сценария.

Пример подключения к уже подготовленному закрытому стенду:

```bash
ssh -N -L 8000:127.0.0.1:8000 deploy-user@your-server.example
```

Здесь имя пользователя и адрес — примеры, которые нужно заменить своими.
Пока туннель открыт, приложение доступно по http://127.0.0.1:8000/.
Открывать порт приложения в интернет для такого режима не требуется.

## Первичная настройка

[ops/bootstrap-staging.sh](../ops/bootstrap-staging.sh) и другие сценарии
`ops/` написаны для конкретной схемы серверных каталогов, пользователя
и ограниченного SSH-доступа. Это не универсальный установщик для любого VPS:
перед применением нужно просмотреть и согласовать эти параметры со своим
окружением.

Bootstrap подготавливает локальные секреты, серверный файл окружения,
root-owned сценарий развёртывания и отдельный SSH-ключ с принудительной
командой. Этот ключ допускает только запрос `deploy:<40-символьный SHA>`;
произвольная shell-сессия и SSH forwarding для него запрещены.

Для GitHub Actions ключ помещается в repository secret
`MISTERCHIP_DEPLOY_SSH_KEY`. Закрытый ключ, серверный `.env`, дампы базы
и содержимое почтового volume должны оставаться вне Git.

Установленный root-owned сценарий — отдельная копия. Изменение файла
в репозитории не обновляет её автоматически: обновление выполняется
администратором после проверки.

## Как работает развёртывание

[Deploy private staging](../.github/workflows/deploy-staging.yml) сначала
выполняет проверки приложения. Затем job развёртывания проверяет отпечаток
SSH-ключа хоста и передаёт серверу точный SHA проверенного коммита.

Сервер проверяет конфигурацию и отсутствие локальных изменений отслеживаемых
файлов, получает `origin/main` и требует совпадения его SHA с запросом.
После этого сценарий:

1. Проверяет Compose и запускает PostgreSQL и Redis.
2. Сохраняет локальный дамп PostgreSQL; при ошибке прекращает развёртывание.
3. Собирает образ и применяет миграции.
4. Выполняет `seed_demo_catalog` и запускает приложение.
5. Проверяет `/healthz/` по локальному HTTP.

Локальный дамп при развёртывании не заменяет внешние резервные копии
и проверку восстановления.

Workflow поддерживает ручной запуск для `main`. В нём также оставлено
узкое правило `push` с фильтром путей и конкретным сообщением коммита.
Условия приведены в самом YAML; обычный pull request с документацией
не запускает развёртывание. Имя workflow историческое и само по себе
не определяет установленный на сервере режим.

## Перед использованием своего сервера

Проверьте соответствие настроек выбранному режиму доступа, установку
ограниченного ключа, домен и TLS для публичного HTTPS, реальные параметры
почты, внешнее резервное копирование и восстановление. Текущие параметры
действующего сервера нужно проверять отдельно: из исходного кода нельзя
сделать вывод о том, что именно уже развернуто.

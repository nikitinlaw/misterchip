## Действующая схема

- Репозиторий: `/home/misterchip-admin/misterchip`.
- VPS: `93.188.187.188`; пользователь `misterchip-admin`.
- `compose.staging.yaml`: PostgreSQL 16, Redis 7, Django/Gunicorn.
- Web опубликован только на `127.0.0.1:8000`; БД и Redis не публикуют порты.
- Caddy обслуживает публичный HTTPS.
- GitHub использует отдельный SSH-ключ с принудительной командой `deploy:<SHA>`.
- Gateway запускает root-owned `/usr/local/sbin/misterchip-deploy`.
  Обновление файлов в Git само по себе не заменяет установленный helper.

Обычная выкладка: **Actions → Deploy private staging → Run workflow → main**.
Сохранён узкий push-trigger для подтверждения Яндекс.Вебмастера; общей выкладки
каждого push он не включает.

## Новая версия deploy helper

1. Проверяет закрытый `.env`, прокси-режим и совпадение SHA с `origin/main`;
   отказывается затирать локальные изменения.
2. Проверяет Compose и запускает БД/Redis при необходимости.
3. Создаёт локальный дамп PostgreSQL перед изменениями.
4. Собирает образ с SHA в `/app/RELEASE` и OCI label.
5. Проверяет SHA нового образа и конфигурацию почты без отправки сообщений.
6. Применяет миграции, запускает web, проверяет `/healthz/` и SHA контейнера.

Локальный дамп находится на том же VPS. Независимое зашифрованное резервирование
и проверка восстановления описаны в OPERATIONS.md.

## Однократное обновление установленного helper

До публичной выкладки M5.1 администратор задаёт в закрытом `.env`
`DJANGO_TRUST_PROXY_CLIENT_IP=1`. Настройка допустима только для Caddy с
private/loopback upstream и без прямого публичного доступа к порту приложения:
IP посетителя берётся из единственного валидного `X-Forwarded-For` только при
private/loopback peer. Новый public helper требует этот флаг; закрытый helper
его не форсирует. Старый установленный helper не устанавливает и не проверяет
настройку, поэтому обычного обновления исходников недостаточно.

Выполняется администратором после проверки коммита и текущего состояния VPS.
Подготовка кода эти команды не запускает. В SSH-сессии `misterchip-admin`,
из каталога репозитория:

```bash
GIT_SSH_COMMAND='ssh -i ~/.ssh/misterchip_github -o IdentitiesOnly=yes' git pull --ff-only origin main
git rev-parse HEAD
sudo install -o root -g root -m 0755 ops/deploy-public-host.sh /usr/local/sbin/misterchip-deploy
```

SHA должен совпадать с проверенным коммитом. После настройки флага и установки
нового helper запускается ручной workflow.
Первая такая выкладка добавит метку версии в образ; старый helper собирал его
без метки.

Для отдельного закрытого стенда используется `ops/deploy-host.sh`. На действующем
публичном сервере повторно запускать `bootstrap-staging.sh` нельзя: он готовит
новый закрытый режим с loopback-hosts и файловой почтой и изменит публичные настройки.

## Закрытый доступ для диагностики

В отдельном терминале доверенного компьютера:

```bash
ssh -N -L 18000:127.0.0.1:8000 \
  -i ~/.ssh/id_ed25519_misterchip -o IdentitiesOnly=yes \
  misterchip-admin@93.188.187.188
```

Для пользовательских сценариев публичного режима используется HTTPS-домен:
secure cookies и ссылки в письмах настроены для него.

## Первоначальная настройка нового закрытого стенда

`ops/bootstrap-staging.sh` сохранён для этой отдельной задачи. Он готовит `.env`,
root-owned helper и ограниченный ключ Actions. Действующие ключи, SMTP-пароли
и `.env` не отправляются в чат и не коммитятся. Секрет Actions уже использовался
в успешных выкладках; заменять его для обычного обновления не требуется.

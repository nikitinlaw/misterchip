# MISTERCHIP — закрытый стенд Beget и автоматическое развёртывание

Важное ограничение: этот процесс **не создаёт публично доступный сайт**.
Django/Gunicorn слушает на сервере **только 127.0.0.1:8000**;
PostgreSQL и Redis не публикуют порты. Доступ из браузера Mac осуществляется
через локальный SSH-туннель. Это промежуточный режим, до настройки домена,
HTTPS, SMTP и резервного копирования за пределы VPS.

## На сервере уже подготовлено

- Beget VPS: Ubuntu 26.04, 2 vCPU, 4 ГБ RAM, 40 ГБ NVMe.
- Пользователь `misterchip-admin` имеет права `sudo`.
- SSH-ключ Mac работает. Удалённый вход root и вход по паролю отключены.
- UFW включён; SSH-порт 22 разрешён.
- Docker 29, Compose 2.40, Git; проект `~/misterchip` получен из приватного GitHub.
- Ключ `~/.ssh/misterchip_github` позволяет VPS только читать репозиторий.

Эти сведения получены при первоначальной настройке; после изменения инфраструктуры
их нужно проверить заново. Контейнеры на VPS на момент подготовки инструкции
не запускались.

## Первоначальная настройка — одна команда на VPS

Открой терминал Mac и подключись обычным SSH-ключом, как ранее. На VPS:

```bash
cd ~/misterchip
GIT_SSH_COMMAND='ssh -i ~/.ssh/misterchip_github -o IdentitiesOnly=yes' git pull --ff-only origin main
bash ops/bootstrap-staging.sh
```

Скрипт без вывода секретов проверит локальный `.env`, сохранит уже заданные
сильные пароли, заменит шаблонные секреты случайными, включит режим
`DJANGO_DEBUG=0` для **локального SSH-туннеля** и файловую тестовую почту
(письма не уходят в интернет).

Он также:
- установит **root-owned** сценарий развёртывания;
- настроит отдельный SSH-ключ GitHub Actions с принудительной командой
  `deploy:<40-символьный SHA>`, без терминала, форвардинга и произвольных команд;
- разрешит выполнение только указанного сценария через `sudo`.

Скрипт спросит пароль **`misterchip-admin`** для административных изменений.

## Один секрет GitHub

На сервере файл `~/.ssh/misterchip_actions_deploy` — **временный закрытый
ключ для GitHub Actions**. Его нельзя отправлять в чат, письмо или коммит.
Выполни `cat ~/.ssh/misterchip_actions_deploy` и скопируй **весь ключ**
непосредственно в GitHub:

[Settings → Secrets and variables → Actions](https://github.com/nikitinlaw/misterchip/settings/secrets/actions)

**New repository secret**:
- Name: `MISTERCHIP_DEPLOY_SSH_KEY`
- Secret: полный многострочный закрытый ключ из файла.

После успешного сохранения секрета удали только временную серверную копию
ключа: `shred -u ~/.ssh/misterchip_actions_deploy`. **Не удаляй** `*.pub`,
`authorized_keys`, ключ Mac или существующий `misterchip_github`.

Этот ключ не даёт GitHub возможность войти в произвольную shell-сессию:
ключ ограничен командой развёртывания, а сервер дополнительно проверяет
точное совпадение SHA с текущим `origin/main`.

## Запуск развёртывания

Перейди в репозиторий GitHub → **Actions → Deploy private staging →
Run workflow → main**.

GitHub Actions:
1. Повторяет миграционные проверки и автоматические тесты с PostgreSQL/Redis.
2. Проверяет SSH-ключ хоста Beget по заранее подтверждённому отпечатку ED25519.
3. Подключается ограниченным ключом и просит развернуть ровно проверенный коммит.
4. На VPS сохраняет закрытый локальный дамп PostgreSQL (не вместо
   последующего внешнего резервного копирования).
5. Собирает образ, применяет миграции, создаёт первоначальный проверочный
   каталог и запускает контейнеры.
6. Проверяет `/healthz/` по локальному HTTP; при ошибке job красный.

**Авторазвёртывание на каждый push пока намеренно не включено.** После
первого безопасного тестового запуска и проверки резервного восстановления
можно привязать этот workflow к успешным тестам ветки `main`. Это исключает
неожиданный запуск на ещё не подготовленном сервере.

## Открываем сайт только у себя на Mac

В **отдельной вкладке терминала Mac**:

```bash
ssh -N -L 8000:127.0.0.1:8000 \
  -i ~/.ssh/id_ed25519_misterchip -o IdentitiesOnly=yes \
  misterchip-admin@93.188.187.188
```

Пока команда работает, открой **http://localhost:8000/** в браузере Mac.
При конфликте порта 8000 на Mac можно использовать
`-L 18000:127.0.0.1:8000` и `http://localhost:18000/`.

**Не открывай** порт 8000 в UFW и не меняй `127.0.0.1:8000:8000` на
`0.0.0.0:8000:8000` — такой тестовый режим на публичной сети небезопасен.
В режиме SSH-туннеля флаги Secure у cookie и HTTPS redirect временно
отключены, но Django DEBUG остаётся выключенным. Для публичного HTTPS
потребуется отдельная конфигурация, восстановление безопасных cookie
и прокси-настроек.

Письма с подтверждением email и сбросом пароля во время пилота
**сохраняются в приватном volume** `mail_data` и не отправляются внешним
адресатам. Для тестирования нужно читать их через защищённый административный
терминал; никогда не публикуй их ссылки в общедоступных логах/чатах.

## Что ещё не сделано

Публичный домен, TLS, реальная почта, внешние/регулярные резервные копии,
проверка восстановления, мониторинг и полная проверка безопасности. Пока
пользователей на сайт не приглашаем. Пароли и ключи **не хранятся в GitHub**,
кроме специально выделенного секретного ключа deploy workflow.

# Локальный запуск MISTERCHIP

Эта инструкция предназначена для просмотра и разработки проекта на своём
компьютере. Используется `compose.yaml`: приложение доступно на
`127.0.0.1:8000`, PostgreSQL и Redis работают внутри сети Docker.
Настраивать рабочий сервер или использовать его ключи не требуется.

## Что понадобится

- Git.
- Docker с командой `docker compose` и поддержкой `up --wait`.
- Доступ к реестрам образов и пакетов для первой сборки.

Команды ниже рассчитаны на shell в macOS, Linux или WSL. В образе проекта
используется Python 3.13, в Compose — PostgreSQL 16 и Redis 7. Версии библиотек,
включая Django, заданы в [`requirements.txt`](../requirements.txt).
Для запуска через Docker отдельно устанавливать Python, PostgreSQL и Redis
на компьютер не нужно.

## 1. Получить проект и собрать образ

Если проект уже скачан, перейдите в его корневой каталог и начните с копирования
`.env.example`.

```bash
git clone https://github.com/nikitinlaw/misterchip.git
cd misterchip
cp .env.example .env
docker compose build web
```

`.env` содержит настройки только вашей локальной копии и не должен попадать
в Git. Не заменяйте им конфигурацию действующего сервера.

## 2. Задать локальные ключ и пароль

После сборки создайте случайное значение:

```bash
docker compose run --rm --no-deps web python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Откройте `.env` в текстовом редакторе и замените значение `DJANGO_SECRET_KEY`
на результат этой команды. Запустите команду ещё раз и используйте новое,
отдельное значение для `DB_PASSWORD`.

Задайте пароль базы **до первого запуска PostgreSQL**: при повторном запуске
с существующим volume переменная окружения не меняет пароль уже созданной
роли базы данных.

Оставьте настройки локального режима из примера:

```dotenv
DJANGO_DEBUG=1
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
DJANGO_EMAIL_BACKEND=django.core.mail.backends.console.EmailBackend
```

Этот режим предназначен исключительно для loopback-доступа на своём
компьютере. Сохраняйте привязку `127.0.0.1:8000:8000` в `compose.yaml`.
Compose самостоятельно задаёт адреса `db` и `redis` для контейнера приложения;
менять `DB_HOST` и `REDIS_URL` вручную для Docker не требуется.

## 3. Создать таблицы и демонстрационный каталог

```bash
docker compose up -d --wait db redis
docker compose run --rm --no-deps web python manage.py migrate --noinput
docker compose run --rm --no-deps web python manage.py seed_demo_catalog
docker compose up -d web
```

При желании перед обычным заполнением можно проверить данные с откатом
изменений. Выполняйте это после миграций:

```bash
docker compose run --rm --no-deps web python manage.py seed_demo_catalog --dry-run
```

`seed_demo_catalog` сам загружает 11 разделов и 373 позиции справочника, затем
создаёт два типа товаров и четыре опубликованные модели: два модуля памяти
Kingston и два резистора YAGEO. В карточках есть ссылки на официальные
спецификации. Отдельно запускать `import_goods` для этого примера не нужно.

Повторный запуск не дублирует модели и не заменяет редакторские изменения
их описаний и значений характеристик. Пользователи, статьи, DIY-проекты,
продавцы, цены, остатки и отзывы этой командой не создаются.

## 4. Проверить результат

```bash
docker compose ps
docker compose exec web python manage.py check
curl --fail --silent --show-error http://127.0.0.1:8000/healthz/
```

Ожидаемый ответ `/healthz/` — `ok`. Он означает, что доступны PostgreSQL и
Redis. Наличие таблиц и содержимое каталога проверяются отдельно через страницы:

| Страница | Что проверить после заполнения новой базы |
| --- | --- |
| [Главная](http://127.0.0.1:8000/) | Отображаются четыре модели каталога. |
| [Поиск Kingston](http://127.0.0.1:8000/catalog/search/?q=Kingston) | В результатах два модуля памяти. |
| [Карточка KF552C40BB-16](http://127.0.0.1:8000/product/kf552c40bb-16/) | Видны характеристики и ссылка на спецификацию. |
| [Каталог](http://127.0.0.1:8000/catalog/search/) | Выберите два модуля Kingston и нажмите сравнение: в таблице различаются значения 5200 и 5600 МТ/с. |

Числовые идентификаторы моделей зависят от базы, поэтому выбирать товары для
сравнения следует через интерфейс. Пустые списки статей и DIY-проектов после
начального заполнения — ожидаемый результат.

### Доступ к административной панели — необязательно

```bash
docker compose exec web python manage.py createsuperuser
```

Задайте собственные имя пользователя, email и пароль по запросам команды.
Затем откройте [административную панель](http://127.0.0.1:8000/admin/).
Готовой общей административной учётной записи в проекте нет.

## Локальная проверка email

В режиме разработки письма подтверждения регистрации и восстановления пароля
не отправляются реальным адресатам. Их содержимое появляется в журнале:

```bash
docker compose logs web
```

После регистрации откройте локальную ссылку из письма в своём браузере и
подтвердите адрес на странице. Ссылки подтверждения и сброса пароля содержат
токены: не публикуйте их вместе с логами или скриншотами.

## Автоматические тесты

Порядок проверок описан в
[`Django checks`](../.github/workflows/tests.yml): установка зависимостей,
проверка миграций, применение миграций, `manage.py check`, проверка сценариев
развёртывания и Compose, сборка статики и `manage.py test`. Проверки используют
PostgreSQL и Redis. Результат конкретного запуска смотрите в GitHub Actions;
наличие workflow не означает, что последний запуск завершился успешно.

Для самостоятельного запуска тестов нужны отдельная тестовая база, доступный
Redis и собранные статические файлы. В локальном Compose весь каталог проекта
монтируется в `/app`, а процесс работает от непривилегированного `appuser`.
На Linux права пользователя хоста могут не позволять этому процессу создать
`staticfiles`. Перед сборкой статики согласуйте права локального каталога;
последовательность CI в отдельном окружении не зависит от этого bind mount.

## Остановка

```bash
docker compose down
```

Данные PostgreSQL и Redis сохранятся в volumes. Для возобновления работы:

```bash
docker compose up -d
```

Флаг `-v` для обычной остановки не нужен: он удаляет volumes вместе с данными.

## Если запуск не получился

| Симптом | Что проверить |
| --- | --- |
| Порт 8000 занят | Освободите порт. Либо измените только локальную привязку на `127.0.0.1:18000:8000` и открывайте страницы на порту 18000. |
| После смены `DB_PASSWORD` приложение не подключается к базе | В существующем volume сохранился прежний пароль роли. Верните соответствующий пароль в `.env` либо отдельно измените пароль роли в PostgreSQL. Удалять данные для обычного запуска не требуется. |
| `/healthz/`, вход или регистрация возвращают 503 | Проверьте состояние и журналы `db` и `redis` через `docker compose ps` и `docker compose logs db redis`. Redis нужен не только для кэша, но и для ограничений запросов. |
| Ошибка про email backend при `DJANGO_DEBUG=0` | Для локального quickstart восстановите `DJANGO_DEBUG=1`. Режим без DEBUG требует отдельной настройки почты и HTTPS; одной смены флага недостаточно. |
| `Permission denied` при чтении `.env` | Файл внутри bind mount должен читаться пользователем `appuser`. Согласуйте владельца, группу или ACL локального каталога. Не применяйте `chmod 600 .env` без проверки доступа контейнерного пользователя. |
| На главной нет моделей или возникает ошибка отсутствующей таблицы | Выполните миграции и `seed_demo_catalog` из шага 3. Успешный `/healthz/` сам по себе не проверяет таблицы приложения и заполнение каталога. |

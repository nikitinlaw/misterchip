# MISTERCHIP — платформа электроники

Первый технический этап проекта: Django + PostgreSQL, одна учётная запись с несколькими бизнес-ролями, каталог конкретных моделей с гибкими характеристиками и отдельный дословный справочник товаров из свидетельства RU № 948080.

**Это каркас разработки, не готовый интернет-магазин.** Продавцы, обзоры, сравнение цен, загрузка драйверов, SaaS/White Label и франшиза будут добавляться по отдельным этапам.

## Требования

Python 3.13, PostgreSQL 16+, Docker Compose (опционально). Используется Django 6.1.1 по исходному учебному проекту. Для защиты исходников Django на продакшене обязательны свои секреты и HTTPS.

## Локальный запуск через Docker

```bash
cp .env.example .env
# установите собственный DJANGO_SECRET_KEY в .env
docker compose up -d --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
```

Сайт: http://127.0.0.1:8000/ ; админка: http://127.0.0.1:8000/admin/.

Вариант без Docker: установите зависимости `pip install -r requirements.txt`, создайте PostgreSQL с реквизитами .env, затем `python manage.py migrate` и `python manage.py runserver`.

## Справочник из свидетельства

В репозитории хранится проверенная CSV-копия `data/trademark_goods_ru948080.csv` из ранее согласованной таблицы. Исходный XLSX остаётся на Google Диске. Для первичной загрузки не требуется вручную скачивать или копировать файл.

```bash
python manage.py import_goods --check-only
python manage.py import_goods
# Для повторной проверки непосредственно по XLSX:
python manage.py import_goods /path/to/MISTERCHIP_catalog_RU948080.xlsx --check-only
```

Команда проверяет заголовки, 11 допустимых категорий, ровно 373 уникальные позиции 1–373. Исходные наименования сохраняются без изменений. Повторный импорт обновляет существующие записи без дублей.

## Гибкие характеристики

Через Django Admin создайте:
1. Раздел каталога `Category` (если ещё не загружен);
2. Тип товара `ProductType`, например «Оперативная память» или «Резистор»;
3. Глобальное определение характеристики `AttributeDefinition` (тип данных и базовая единица);
4. Связь `ProductTypeAttribute` с нужным типом товара;
5. Конкретную модель `Product` и её значения `ProductAttributeValue`.

Характеристики типов настраиваются в данных, без переписывания модели Python; числовые единицы автоматически нормализуются только для явно предусмотренных совместимых величин. В административной карточке сохранённой модели появилась ссылка **«Настроить характеристики»**. Страница автоматически строит подходящие поля и единицы измерения для выбранного типа товара, проверяет обязательные значения и нормализует допустимые единицы. Смена типа уже созданной модели через Admin заблокирована во избежание потери смысла параметров.

## Публичный поиск и сравнение

- `/catalog/search/` — поиск по названию, модели, артикулу, бренду; фильтрация по разделу, типу, производителю и характеристикам. Числовые фильтры задаются в канонической единице (например, в Ом), даже если карточка товара хранит значение в кОм.
- В результатах можно отметить от двух до четырёх моделей **одного типа** и открыть `/catalog/compare/`; технические параметры сравниваются по общим определениям и нормализованным значениям. Смешанные типы не сравниваются.
- Главная страница отображает опубликованные модели и ссылки на разделы. Эти страницы — функциональная основа интерфейса, полноценный дизайн и SEO предстоит разработать отдельно.

## Учётные записи и редакция

Появились публичные страницы `/account/register/`, `/account/login/`,
закрытый кабинет `/account/profile/` и публичный профиль автора
`/account/authors/<username>/`. Один пользователь может совмещать роли автора,
обзорщика и разработчика. Роль покупателя назначается при регистрации.
Редакторские права, а также проверенные статусы продавца и представителя
производителя **нельзя самостоятельно получить через форму регистрации** —
они назначаются администрацией отдельно.

Раздел `/articles/` содержит только опубликованные материалы.
Автор с ролью `author` создаёт черновик через `/articles/new/`, связывает
его с опубликованными товарными карточками и отправляет редактору.
Редакторы с правами Django Admin используют действия **«Опубликовать»**,
**«Отклонить»**, **«Снять с публикации»**. Черновики и отправленные материалы
недоступны публично, а автор не может незаметно изменить уже одобренный
текст. Связанные статьи отображаются в карточке модели.

Тело статьи хранится обычным текстом (не исполнение HTML/JavaScript).
Для ссылок на видео и внешние источники используются URL, файлы третьих лиц
не копируются. При создании требуется подтверждение прав на материалы.

**Перед публичным запуском** дополнительно нужны проверка электронной почты,
восстановление пароля, ограничение частоты регистрации и входа, антиспам,
политика обработки персональных данных и подробный регламент проверки прав
на публикации. Сейчас регистрация MVP не подтверждает владение email.

## Подтверждение email, пароли и ограничения запросов

У новой регистрации адрес электронной почты подтверждается по ссылке. Учётная
запись создаётся с `is_active=False` и **не может войти или публиковать
материалы до подтверждения email**. Ссылка подписывается ключом Django и
действует **24 часа**. Открытие ссылки само по себе ничего не активирует:
пользователь должен нажать кнопку подтверждения на странице (POST + CSRF).
После активации ссылка становится одноразовой. Повторное письмо можно
запросить через `/account/resend-verification/`, с одинаковым сообщением для
неизвестных и уже подтверждённых адресов.

Забытый пароль восстанавливается стандартной защищённой процедурой Django:
`/account/password-reset/` отправляет ссылку только на активную учётную
запись; пользователю сообщается одинаковый результат независимо от наличия
адреса в базе. Срок действия ссылки — **1 час**. Старые пароли при восстановлении
не передаются по электронной почте.

Простая распределённая защита от автоматических запросов использует счётчики
Redis: вход — **20 POST за 15 минут**, регистрация — **8 в час**, восстановление
пароля и повторное подтверждение — по **6 в час**, попытки подтверждения — **20
за 15 минут**, на IP-адрес для каждого маршрута. При недоступности Redis
операции входа/регистрации и восстановления пароля возвращают HTTP 503,
**не обходя ограничения**. Ответ при превышении лимита — HTTP 429 с
`Retry-After`. Адрес берётся только из `REMOTE_ADDR`; произвольный
`X-Forwarded-For` игнорируется. При использовании обратного прокси необходимо
правильно настроить доверенную передачу адреса клиента и защититься от
подделки IP-заголовков. Для серьёзного публичного трафика потребуется
дополнительная противоботовая защита на границе (WAF, anti-abuse).

### Настройка для локального запуска

```bash
cp .env.example .env
# задайте уникальный DJANGO_SECRET_KEY
docker compose up -d --build
docker compose exec web python manage.py migrate
```

Compose запускает PostgreSQL и Redis. По умолчанию в режиме разработки
письма **не отправляются реальным адресатам**, а печатаются в журнал
контейнера. Проверить ссылку можно через `docker compose logs web`.
Это предназначено только для локальной проверки.

### Перед запуском на настоящем домене

Подключить реальный SMTP-провайдер через `DJANGO_EMAIL_BACKEND`,
`EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`,
`EMAIL_USE_TLS` и `DEFAULT_FROM_EMAIL`. Настроить SPF/DKIM/DMARC для домена;
хранить пароли и ключи вне GitHub, не запускать с `DJANGO_DEBUG=1`.
Обязательно HTTPS, корректные `DJANGO_ALLOWED_HOSTS`, безопасные cookie,
доверенная схема обработки прокси и отдельная сеть для PostgreSQL/Redis.

Пока **не выполнены** аудит обработки персональных данных и публичный security
review, продукт не считается готовым к открытой регистрации. Резервное
копирование, мониторинг ошибок, тестирование реальных писем и защита от
сложных распределённых атак также остаются задачами перед запуском.

## DIY-проекты: схемы, BOM, прошивки и файлы 3D-печати

Отдельный раздел `/projects/` — не разновидность статьи, а самостоятельная
сущность `Project`, связанная с автором и опубликованными моделями товаров.
У проекта имеются описание, пошаговая инструкция, условия лицензирования,
редакционный статус, **BOM (ProjectComponent)** и **внешние технические ссылки
(ProjectResource)**: схемы, PCB, прошивки, открытый исходный код, STL/3D, видео
и документация. Именование компонентов в BOM не зависит от существования
ссылки на карточку модели в каталоге. Количество хранится числом с единицей.

Пользователь с ролью `developer` или `author` может создать проект через
`/projects/new/`, заполнить пару строк BOM и технических ресурсов, сохранить
черновик, после проверки авторских прав отправить редактору. Редактор через
Django Admin одобряет, отклоняет либо снимает проект с публикации.
Черновики не видны публике; утверждённые проекты показываются также в
карточках соответствующих товаров и на странице их авторов.

В этой первой версии имеются **только HTTPS-ссылки на внешние файлы**, без
загрузки пользовательских прошивок, ZIP, STL или иных файлов на сервер.
Это снижает риск распространения вредоносных файлов и нарушений прав при
пилотной эксплуатации. Перед включением прямых загрузок необходимы
контроль лицензий, сканирование файлов, ограничения размеров, Object
Storage, версионирование и отдельный домен для недоверенного контента.
Редактор должен проверять техническую безопасность инструкций.

## Архитектурные принципы

- `accounts.User` — собственная модель пользователя до первых миграций; `UserRole` поддерживает несколько ролей.
- `TrademarkGood` хранит формулировки 9-го класса МКТУ **отдельно** от реальных моделей `Product`.
- `Category` — 11 широких разделов интерфейса; `ProductType` — внутренний технический тип модели.
- `AttributeDefinition` и `ProductTypeAttribute` — справочник характеристик и настройка набора по типу.
- Продавец и его цена будут отдельными сущностями, общая карточка модели не станет объявлением отдельного продавца.
- Не переносим код дипломного проекта без проверки; исходный репозиторий [Python_Site_FinalProject_Nikitin](https://github.com/nikitinlaw/Python_Site_FinalProject_Nikitin) не изменяется.

## Ограничения текущей стадии

Ещё не реализованы верификация электронной почты, восстановление доступа, антиспам/ограничение частоты запросов, загрузки изображений, импорт прайсов продавцов и полноценные DIY-проекты с BOM и файлами. Базовые кабинеты авторов, статьи и редакционная модерация уже реализованы. Производственный сервер и регулярные резервные копии не развернуты.
